# TP06 – Real-Time Data Processing Using Apache Spark Structured Streaming and Apache Flink

## 1. Project Overview

This project implements a real-time smart-campus event processing system using Apache Kafka, Apache Spark Structured Streaming, and Apache Flink SQL.

The system simulates student activities using QR/RFID events, such as check-ins, opening courses, and entering the library.

Events are generated by a Python producer, published to a Kafka topic, and processed in real time by Spark Structured Streaming.

The main objectives are:

- Generate synthetic campus events.
- Ingest events using Apache Kafka.
- Process JSON events using Spark Structured Streaming.
- Perform window-based aggregations.
- Detect late student check-ins.
- Monitor ingestion and processing rates.
- Explore event-time processing and watermarks.
- Demonstrate checkpointing and recovery.
- Explore Apache Flink SQL for stream processing.

## 9. Questions for the Report

### Question 1: What is the difference between Kafka's role and Spark/Flink's role in the pipeline?

Apache Kafka is responsible for receiving, storing, and distributing streaming events. It acts as a message broker between producers and consumers.

Apache Spark and Apache Flink are processing engines. They consume events from Kafka, perform transformations, aggregations, filtering, and event-time analysis, and produce useful results.

In this project, Kafka transports campus events, while Spark processes them to calculate event counts and detect late check-ins.

### Question 2: Explain how Spark Structured Streaming represents a stream and updates a result incrementally.

Spark Structured Streaming represents a continuous stream of data as an unbounded table.

New incoming events are treated as new rows added to this table.

Spark processes incoming data incrementally and updates the result table as new events arrive.

For example, when a new student check-in event arrives, Spark updates the count for the corresponding department and time window.

### Question 3: What is a micro-batch? Give one advantage and one trade-off.

A micro-batch is a small group of streaming records processed together during a short time interval.

Spark Structured Streaming commonly uses micro-batch processing.

**Advantage:** It provides scalable processing and integrates well with Spark's batch-processing engine.

**Trade-off:** It introduces some processing delay because records are processed in batches rather than individually.

### Question 4: What is the purpose of the Kafka source options startingOffsets and subscribe?

The `subscribe` option specifies the Kafka topic from which Spark reads messages.

Example:

```python
.option("subscribe", "campus-events")
```

The `startingOffsets` option specifies where Spark starts reading messages when initializing a new streaming query.

Example:

```python
.option("startingOffsets", "earliest")
```

- `earliest`: Starts reading from the earliest available offsets.
- `latest`: Starts reading only newly arriving messages.

When a checkpoint already exists, Spark uses the saved progress information for recovery rather than simply restarting from the configured starting offset.

### Question 5: Why is the JSON schema explicitly defined before parsing the event values?

An explicit schema tells Spark the expected structure and data types of incoming JSON messages.

For example:

- `eventId`: Integer.
- `studentId`: String.
- `eventType`: String.
- `department`: String.
- `eventTime`: String.

Defining the schema helps Spark interpret the data correctly, avoids unnecessary schema inference, and makes the parsing process more efficient and predictable.

### Question 6: Distinguish event time and processing time using one event from your experiment.

**Event time** is the timestamp indicating when the event actually occurred, as provided in the event's `eventTime` field.

**Processing time** is the time when Spark processes the event.

In this experiment, the Producer generated events with timestamps using:

```python
event_time = base + timedelta(milliseconds=offset_ms)
```

For example, an event may have an event time of 19:08:00, but Spark may process it in a later batch.

The difference occurs because Kafka transport, buffering, and Spark scheduling can introduce delays.

Event time is important for accurate window-based analysis because it reflects when the event occurred rather than when it was processed.

### Question 7: What is a watermark? Does it guarantee that no late event will be lost? Explain.

A watermark is a mechanism used by Spark Structured Streaming to manage late-arriving events and control how long the engine keeps event-time state.

For example:

```python
.withWatermark("event_ts", "30 seconds")
```

This configures a 30-second lateness threshold relative to the maximum event time observed by the query.

A watermark does not guarantee that no late event will be lost.

Events arriving later than the allowed watermark threshold may be discarded from stateful aggregations.

Therefore, a watermark provides a practical balance between handling delayed events and limiting the amount of state maintained by Spark.

### Question 8: Compare tumbling, sliding, and session windows.

**Tumbling windows**

- Have a fixed duration.
- Do not overlap.
- Each event belongs to one window for a given window definition.

Example: A one-minute tumbling window.

**Sliding windows**

- Have a fixed duration and a slide interval.
- Overlap when the slide interval is shorter than the window duration.
- An event can belong to multiple windows.

Example: A two-minute window sliding every 30 seconds.

**Session windows**

- Have dynamically determined boundaries.
- Group events according to periods of activity separated by inactivity gaps.
- Events belonging to the same session are grouped together.

Example: Student activity events separated by no more than five minutes can belong to the same session.

### Question 9: What information does a checkpoint preserve, and why must its location remain stable during a recovery test?

A Spark checkpoint preserves streaming progress and the state required by stateful operations.

It includes information such as:

- Source offsets.
- Batch progress and commit information.
- Stateful processing information, when applicable.

The checkpoint location must remain stable because Spark uses it to identify the previous progress of the streaming query.

If the same query is restarted with its original checkpoint, Spark can resume processing from the saved progress instead of starting over.

Using a different checkpoint location creates a new query state and does not demonstrate recovery from the previous checkpoint.

Each independent streaming query should have its own checkpoint directory.

### Question 10: Give two differences between Spark Structured Streaming and Flink based on the lecture.

**Difference 1: Processing model**

Spark Structured Streaming commonly uses micro-batch processing, although it also provides a continuous processing mode with different limitations.

Apache Flink is designed around continuous stream processing and processes records as they arrive.

**Difference 2: State and event-time processing**

Both engines support event-time processing, watermarks, and stateful operations.

However, Flink provides a native event-driven streaming runtime with extensive support for state management and event-time operations, while Spark Structured Streaming integrates streaming operations with the Spark SQL and DataFrame ecosystem.

### Question 11: Which engine would you select for this smart-campus scenario and why?

For this smart-campus scenario, I would select Apache Spark Structured Streaming.

The reasons are:

**Latency:** Spark's micro-batch model provides practical near-real-time processing, although it can introduce some delay. This is suitable for campus check-in monitoring and event aggregation.

**Event-time handling:** Spark supports event-time processing, watermarks, and tumbling and sliding windows.

**State management:** Spark supports stateful aggregations and checkpointing for recovery.

**Ecosystem:** Spark integrates well with Python, SQL, Kafka, DataFrames, and other data-processing tools.

**Team skills:** A team already familiar with Python and Spark can develop and maintain the solution more easily.

Flink would also be a strong choice, particularly when very low latency and continuous event-driven processing are major requirements.

For this project, Spark provides a practical balance between functionality, integration, and development simplicity.
